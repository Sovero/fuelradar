# Техническое задание

## FuelRadar — система мониторинга доступности топлива на АЗС

**Версия:** 1.0
**Дата:** 07.09.2026
**Тип решения:** PWA / веб-приложение
**Основной регион пилотирования:** Краснодар

# 1. Назначение системы

FuelRadar предназначен для оперативного поиска и мониторинга автозаправочных станций с необходимым видом топлива.

Система должна агрегировать информацию из нескольких источников, сопоставлять данные об одной и той же физической АЗС, определять наличие топлива, оценивать актуальность и достоверность информации, учитывать очереди и уведомлять пользователя о значимых изменениях.

Основной пользовательский сценарий:

> Найти, где поблизости сейчас действительно есть нужный бензин, насколько достоверна эта информация, есть ли очередь и сколько времени потребуется, чтобы добраться и заправиться.

---

# 2. Основные принципы системы

## 2.1. Независимость от одного источника

Запрещается строить систему вокруг Яндекс Карт, 2ГИС, Т-Банка либо другой единственной внешней системы.

FuelRadar должен иметь собственный каталог АЗС.

Он формируется как объединение:

* картографических сервисов;
* официальных данных топливных сетей;
* агрегаторов;
* пользовательских данных;
* открытых источников;
* иных подключаемых источников.

---

## 2.2. АЗС и информация о наличии топлива — разные сущности

Необходимо чётко разделить:

**Discovery:**
существует ли физически АЗС и где она расположена.

**Availability:**
какое топливо на данной АЗС доступно сейчас.

Например, если Лукойл присутствует в 2ГИС, но отсутствует в Яндексе, FuelRadar всё равно должен отображать эту АЗС.

Если АЗС обнаружена, но ни один источник не предоставляет сведения о топливе:

> Статус топлива: нет актуальных данных.

а не:

> Топлива нет.

Это принципиальное требование.

# 6. Главный объект системы — АЗС

Каждая физическая АЗС должна иметь внутренний идентификатор:

```text
station_id
```

Например:

```text
fr_station_000184
```

Он не должен зависеть от ID Яндекса, 2ГИС или другой системы.

# 9. Мастер-каталог АЗС

Система должна регулярно формировать собственный актуальный каталог.

Архитектурный принцип:

```text
Яндекс ──────┐
2ГИС ────────┤
OSM ─────────┤
Лукойл ──────┤
Роснефть ────┤
Газпром ─────┤──► Normalization
Другие сети ─┤          │
Пользователи ┤          ▼
Другие ──────┘     Deduplication
                         │
                         ▼
                  MASTER STATIONS
```

# 10. Дедупликация

Разные источники могут описывать одну АЗС:

```text
Лукойл
ЛУКОЙЛ
АЗС Лукойл №47
Lukoil
АЗС №47
```

как разные организации.

Система должна определить, что это одна станция.

---

# 11. Алгоритм сопоставления

При дедупликации учитывать:

1. расстояние между координатами;
2. бренд;
3. адрес;
4. номер АЗС;
5. телефон;
6. название;
7. географическую близость въезда;
8. дополнительные признаки.

Можно применять weighted matching.

Например:

```text
coordinates = 50%
brand       = 20%
address     = 15%
name        = 10%
phone       = 5%
```

При достаточно высокой вероятности записи объединяются автоматически.

При средней вероятности:

> Требует подтверждения администратора.

# 14. Важное ограничение интеграций

Для каждого источника перед разработкой адаптера необходимо определить:

* существует ли официальный API;
* допускает ли лицензия использование данных;
* доступны ли данные по конкретным видам топлива;
* доступны ли очереди;
* период обновления;
* rate limit;
* стоимость API;
* требования к хранению;
* возможность кэширования;
* запрет/разрешение автоматизированного получения данных.

Если оперативные данные доступны только в интерфейсе сервиса, но официальный API отсутствует, такой источник должен быть отмечен:

```text
RESEARCH_REQUIRED
```

Нельзя молча строить критическую часть продукта на нестабильном scraping.

# 16. Нормализация топлива

Разные источники могут использовать:

```text
95
АИ-95
AI95
95 Экто
95 G-Drive
95 Pulsar
Premium 95
```

Система должна понимать:

```text
base_fuel = AI_95
commercial_name = ЭКТО
```

То есть пользователь сможет выбрать:

> любой АИ-95

или:

> только ЭКТО-95.

---

# 17. Статусы топлива

Необходимо использовать не бинарное поле `есть/нет`, а расширенную модель.

```text
AVAILABLE
LIKELY_AVAILABLE
LOW_STOCK
UNCERTAIN
UNAVAILABLE
UNKNOWN
```

В интерфейсе:

| Статус           | Представление |
| ---------------- | ------------- |
| AVAILABLE        | Есть          |
| LIKELY_AVAILABLE | Вероятно есть |
| LOW_STOCK        | Заканчивается |
| UNCERTAIN        | Под вопросом  |
| UNAVAILABLE      | Нет           |
| UNKNOWN          | Нет данных    |

---

# 18. Главное различие UNKNOWN и UNAVAILABLE

**UNAVAILABLE**

Источник сообщает:

> АИ-95 отсутствует.

**UNKNOWN**

Система не знает, есть АИ-95 или нет.

Эти состояния нельзя смешивать.

---

# 19. Временная актуальность

Любые оперативные данные должны содержать:

```text
observed_at
received_at
source
expires_at
```

Например:

> АИ-95 есть
> подтверждено 14 минут назад.

Если сведения старые, confidence автоматически уменьшается.

---

# 20. История

Необходимо хранить исторические наблюдения.

Пример:

```text
station_id: FR-001
fuel: AI_95

10:00 AVAILABLE
11:00 AVAILABLE
12:00 AVAILABLE
13:00 LOW_STOCK
14:00 UNAVAILABLE
15:00 UNAVAILABLE
18:00 AVAILABLE
```

История должна сохраняться, а не перезаписываться.

---

# 21. Confidence Score

Каждому итоговому статусу присваивается достоверность:

```text
0–100%
```

Учитываются:

* доверие к источнику;
* давность информации;
* количество независимых источников;
* совпадение источников;
* пользовательский рейтинг;
* геолокационное подтверждение;
* конфликт данных.

---

# 22. Пример расчёта

Допустим:

официальный источник:

> АИ-95 есть — 15 минут назад.

Яндекс:

> есть — 20 минут назад.

Пользователь непосредственно на АЗС:

> есть — 5 минут назад.

Результат:

```text
AVAILABLE
confidence = 97%
```

---

# 23. Конфликт источников

Например:

```text
Источник A: AVAILABLE
Источник B: UNAVAILABLE
Источник C: AVAILABLE
```

FuelRadar не должен просто выбирать последнее сообщение.

Необходимо учитывать:

* качество;
* время;
* количество подтверждений.

И можно получить:

```text
LIKELY_AVAILABLE
Confidence 67%
```

# 27. Географический мониторинг

Поддержать четыре типа зоны.

```text
CITY
CIRCLE
POLYGON
ROUTE_CORRIDOR
```

---

# 28. CITY

Например:

> Краснодар.

Выбираются АЗС, географически находящиеся в границах города.

---

# 29. CIRCLE

Например:

> 15 км от текущего местоположения.

Параметры:

```text
lat
lon
radius
```

---

# 30. POLYGON

Пользователь либо администратор может обозначить произвольную территорию.

Например:

> Краснодар + Яблоновский + Новая Адыгея.

---

# 31. ROUTE_CORRIDOR

АЗС вдоль маршрута.

Например:

> Краснодар → Минеральные Воды.

Параметр:

```text
distance_from_route <= 5 km
```

---

# 32. Текущее местоположение

Пользователь может включить:

> Следить вокруг меня.

Например:

```text
Radius: 20 km
```

Если пользователь перемещается в другой регион, область поиска меняется.

---

# 33. Режимы геолокации

Необходимо предусмотреть:

### Статическая зона

Краснодар + 10 км.

### Динамическая зона

Текущая позиция + 15 км.

### Динамическая со сменой города

Если пользователь переместился достаточно далеко, система автоматически перестраивает мониторинг.

---

# 34. Контроль приватности

Геолокация используется только после явного разрешения.

Пользователь должен иметь возможность:

* выключить использование GPS;
* использовать выбранную вручную точку;
* удалить историю геопозиции.

Для работы приложения необязательно постоянно хранить историю перемещений.

# 129. Критерии готовности MVP

MVP считается готовым, когда:

1. Система формирует мастер-каталог АЗС Краснодара минимум из двух независимых источников.
2. Выполняется дедупликация.
3. Есть карта.
4. Есть список.
5. Работает GPS.
6. Работает поиск по радиусу.
7. Есть фильтр по сети.
8. Есть AI-92, AI-95 и ДТ.
9. Есть состояния AVAILABLE / UNAVAILABLE / UNKNOWN.
10. Видно время обновления.
11. Рассчитывается Confidence.
12. Есть избранное.

# 141. Ключевой архитектурный принцип

FuelRadar не должен быть:

> интерфейсом над Яндексом.

Он должен быть:

> **системой независимой агрегации, нормализации, сопоставления и оценки оперативной информации об АЗС.**

Именно поэтому Яндекс может видеть 120 станций, 2ГИС — 170, OSM — 155, официальные сети — ещё несколько, а FuelRadar после сопоставления сформирует, условно:

> **183 реальные уникальные АЗС.**

---

# 142. Целевой пользовательский результат

Идеальный ответ приложения должен выглядеть примерно так:

> **АИ-95 найден.**
>
> **Лукойл, ул. …**
>
> 4,6 км · 11 минут
> АИ-95: **есть**
> Достоверность: **94%**
> Подтверждено: **8 минут назад**
> Очередь: **небольшая, ~7 минут**
>
> Ориентировочное время до заправки: **18 минут**.
>
> Ещё две АЗС с АИ-95 находятся в радиусе 10 км.

А если топлива нет:

> **Подтверждённого АИ-95 в радиусе 10 км сейчас не найдено.**
>
> Есть две станции со статусом «вероятно есть».
>
> Ближайшая — 8,2 км, достоверность 64%.
>
> **[Увеличить радиус] [Следить за появлением]**

Вот это я считаю целевой моделью FuelRadar.
