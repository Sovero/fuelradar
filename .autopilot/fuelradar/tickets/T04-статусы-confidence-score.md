## Что должно заработать

Агрегация наблюдений (station, fuel) в итоговый статус + confidence 0–100% + разбор
вкладов. Наборы статусов топлива (AVAILABLE…UNKNOWN) и очередей (NONE…VERY_HIGH).
**Инвариант: UNKNOWN никогда не конвертируется в UNAVAILABLE и наоборот** (R15) —
проверяется тестом. Конфликт источников агрегируется (качество, время, число
подтверждений), а не «последнее сообщение». Свежесть: observed_at/received_at/expires_at,
TTL (топливо 2 ч, очередь 30 мин — конфиг §18), устаревание → UNKNOWN, не «нет» (R56).
Очередь: уровень + исходное число машин + estimated_wait_minutes. Веса: GPS < 300 м (R40),
reliability_score (R41, базовый счёт). FuelRadar Score (fuel_available, confidence,
freshness, distance, travel_time, queue, приоритеты сетей R77) с `score_breakdown`
(R43/R44/R45). История наблюдений не перезаписывается (R17); результат — в
`station_current_status` (R16).

> «AVAILABLE / LIKELY_AVAILABLE / LOW_STOCK / UNCERTAIN / UNAVAILABLE / UNKNOWN»

## Критерии приёмки

- [ ] Инвариант UNKNOWN ≠ UNAVAILABLE: тест на чистой функции агрегации и валидатор API
- [ ] Один источник «есть» (15 мин) + Яндекс «есть» (20 мин) + 2 пользователя (5–9 мин) → AVAILABLE ~97%-типа; разбор вкладов виден
- [ ] Конфликт A: есть / B: нет → не крайний статус, а LIKELY_AVAILABLE/UNCERTAIN с пониженным confidence
- [ ] Наблюдение старше TTL топлива → статус UNKNOWN (не UNAVAILABLE), confidence падает
- [ ] queue_vehicles сохраняется оригиналом; estimated_wait_minutes считается по конфигу, без данных — null
- [ ] Score выбирает станцию Б (5 км, 96%, очередь 5 мин) перед станцией А (2 км, 45%, 30 мин); `score_breakdown` в ответе
- [ ] Приоритет сети (R77) влияет на Score только как множитель сортировки
- [ ] Отчёт с GPS < 300 м имеет повышенный вес; reliability_score базово считается
- [ ] История: новое наблюдение — новая строка; `station_current_status` пересчитывается
- [ ] Unit-тесты: aggregate (конфликты, свежесть, веса), score (разбор), TTL-устаревание
