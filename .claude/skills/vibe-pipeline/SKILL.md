# Vibe-Pipeline: пять шагов вместо «дал промпт — жду результат»

Обычный вайбкодинг уязвим в четырёх местах:

1. **Промпт без деталей** — агент сам решает, что и как делать; нет критериев
   выполненности.
2. **Контекст** — агент забывает, что делает, по мере длинного диалога.
3. **Проверка кода** — «Готово, всё работает» никто не проверял.
4. **Workflow** — работает один агент, последовательно, без изоляции.

Пайплайн ниже закрывает все четыре. Пять шагов: **опрос → план и спецификация →
тесты до кода → оркестратор → изоляция**. Проходить их по порядку; шаги 1–3
обязательны всегда, шаги 4–5 — для задач, которые весят больше одного хода.

---

## Шаг 1. Опрос: агент задаёт вопросы первым

Никогда не начинать кодить по неразвёрнутому промпту. До любой реализации
задать пользователю уточняющие вопросы (структурированно, с вариантами ответов):

- Какая цель и какой измеримый результат? Что будет считаться «готово»?
- Что входит в скоуп, а что — заведомо нет?
- Ограничения: стек, совместимость, сроки, что ломать нельзя.
- Кто пользователь результата и какие у него сценарии?

После ответов сформулировать полный промпт задачи и показать его пользователю.
Неразвёрнутый промпт после опроса обрастает «мясом»: вопрос с тремя–пятью
вариантами ответа стоит секунды, а экономит часы переделки.

## Шаг 2. План и спецификация: контекст на disk, не в диалоге

Готовые заготовки обоих файлов лежат рядом в [templates/spec.md](templates/spec.md)
и [templates/plan.md](templates/plan.md) — копировать их в `vibe/` и заполнять,
а не изобретать структуру заново.

Нейросети забывают задачу по мере роста диалога. Поэтому контекст — в файлы,
а не только в историю чата:

- `vibe/spec.md` — спецификация: что строим, границы, инварианты, явно
  перечисленное «что НЕ делаем». Точка истины при любом споре «а как надо».
- `vibe/plan.md` — план: атомарные шаги-чекбоксы, у каждого — критерий
  выполненности (как проверить, что пункт закрыт) и список затрагиваемых файлов.

Держать эти файлы открытыми в каждой итерации: перечитывать перед началом
шага и сверяться после. Спецификация держит агента в одном направлении и
снижает галлюцинации; план — превращает «сделай авторизацию» в проверяемые
пункты.

## Шаг 3. Тесты до кода: ТЗ, которое нельзя понять двояко

Тест — маленькая программа, проверяющая другую программу: «такой вход → такой
выход», запускается одной командой, результат — зелёный или красный.

Почему **до** кода:

- План говорит «сделай авторизацию». Тест говорит: «логин с верным паролем →
  токен в ответе; с неверным → 401; три неверных → блокировка на минуту».
  Это уже не пожелание, а контракт: агент пишет код так, чтобы контракт
  выполнялся, а не «как получится».
- Тесты, написанные после кода, агент подгоняет под то, что уже сделал, —
  они всегда зелёные и проверяют не то, что вы хотели.
- «Готово, всё работает» — вежливость, а не факт. Тесты превращают её в факт:
  зелёный прогон обязателен, красный — работа не готова.

Порядок действий:

1. По спецификации составить тесты **для каждого пункта плана**: что
   проверяем, какой вход, какой ожидаемый результат.
2. Запустить тесты и убедиться, что они **красные** — кода ещё нет, и это
   нормально. Красный тест до кода = честный контракт.
3. Писать код, пока все тесты не станут зелёными. После каждого изменения
   запускать тесты самому; при падении читать ошибки и чинить, а не
   возвращать проблему пользователю.

Цикл: написал → запустил → увидел красное → починил → зелёное. Без тестов
ошибку ищет пользователь (и не всегда находит); с тестами её находит агент —
сразу в процессе работы.

## Шаг 4. Оркестратор: умная модель раздаёт, дешёвые выполняют

Когда план большой, один агент работает часами. Тогда:

- **Оркестратор** (умная модель) делит план на независимые подзадачи,
  для каждой составляет критерии валидации и отдаёт подзадачу воркеру.
- **Воркеры** (дешёвые модели) выполняют подзадачи параллельно по своим
  кусочкам плана и тестам.
- Оркестратор собирает результаты, проверяет по критериям валидации,
  интегрирует и держит общий контекст (spec/plan).

Эффект: токены умной модели тратятся на планирование и контроль, а не на
рутину; время разработки сжимается за счёт параллельных исполнителей.

## Шаг 5. Изолированные ветки: git worktree на каждого воркера

`git worktree` — независимая копия рабочего каталога проекта на своей ветке,
не затрагивающая основную версию:

```bash
# по воркеру на подзадачу, из чистого основного чекаута
git worktree add ../proj-feat-auth -b feat/auth
git worktree add ../proj-feat-billing -b feat/billing

# воркер работает внутри своего каталога; основной остаётся чистым
cd ../proj-feat-auth && <запуск агента с подзадачей и её тестами>

# после валидации оркестратором — мердж и уборка
git checkout main && git merge --no-ff feat/auth
git worktree remove ../proj-feat-auth && git branch -d feat/auth
```

Параллельные агенты ничего не ломают друг другу и основную версию;
конфликты решаются при мердже, а не посреди работы.

## Промпты: как это выглядит на практике

Дословные формулировки промптов из первоисточника — копировать и подставлять
свою задачу. Промпты шага 3 — дословно из видео; остальные — в той же логике
по шагам пайплайна.

**Шаг 1 — опрос** (вместо сразу задачи — сначала вопросы, потом код):

```
Прежде чем что-то делать, задай мне уточняющие вопросы по этой задаче —
по одному, с вариантами ответов. Только после моих ответов сформулируй
полный промпт задачи и покажи его мне на подтверждение.
```

**Шаг 2 — план и спецификация** (после опроса):

```
На основе моих ответов составь план атомарными шагами со спецификацией:
у каждого шага — критерий выполненности и затрагиваемые файлы.
Спецификацию и план сохрани в vibe/spec.md и vibe/plan.md — дальше
сверяйся с ними в каждом шаге.
```

**Шаг 3 — тесты до кода.** После плана пишете агенту буквально так
(дословно из видео):

```
Прежде чем писать код, составь тесты по этой спецификации для каждого
пункта плана: что мы проверяем, какой вход и какие ожидаемые результаты.
Запусти их и убедись, что они красные. Да, красные — это нормально:
кода ещё нет и проверять пока нечего.
```

Затем следующая команда (дословно из видео):

```
Теперь пиши код, пока все тесты не станут зелёными. После каждого
изменения запускай тесты сам. Если упало — читай ошибки и чини,
а не проси меня.
```

Агент начинает крутить цикл: написал → запустил → увидел красное →
починил → запустил зелёное. Это и есть та обратная связь, которой нет
в схеме «дал промпт и жду результат».

**Шаги 4–5 — оркестратор и изоляция** (когда план большой):

```
Раздели план на независимые подзадачи. Для каждой — свой воркер,
отдельная git worktree-ветка и пункты валидации из spec.md.
Ты — оркестратор: распределяешь подзадачи, следишь за выполнением
по критериям, собираешь и интегрируешь результаты после валидации.
Основной чекаут не трогаем до успешного мерджа.
```

## Чек-лист завершения задачи

- [ ] Опрос проведён, ответы зафиксированы в spec.
- [ ] `vibe/spec.md` и `vibe/plan.md` существуют и актуальны.
- [ ] Тесты написаны ДО кода и сначала были красными.
- [ ] Финальный прогон всех тестов зелёный (показан пользователю).
- [ ] Подзадачи выполнялись в изолированных worktree и слиты после валидации.
- [ ] Ни один пункт плана не закрыт без критерия выполненности.
