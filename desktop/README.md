# FuelRadar Desktop

Windows-приложение (Electron) поверх того же веб-интерфейса: установщик NSIS,
автообновление через electron-updater, вход через Telegram.

## Архитектура

```
┌─ FuelRadar.exe (Electron) ──────────────────────────────┐
│  окно → http://127.0.0.1:<прокси-порт>                  │
│  reverse-proxy (аналог deploy/Caddyfile из прода):      │
│    /api/* → backend (FUELRADAR_API_URL / config.json),  │
│             Origin переписывается (R66, иначе 403);     │
│    /*     → встроенный Next standalone (server-dist)    │
│  backend по умолчанию — свой, из resources/backend      │
│  (замороженный Python: ставить на машине нечего)        │
└──────────────────────────────────────────────────────────┘
```

- Встроенный интерфейс: `desktop/server-dist` — production-сборка Next.js
  (`NEXT_OUTPUT=standalone`), запускается самим Electron
  (`ELECTRON_RUN_AS_NODE=1`) на свободном 127.0.0.1-порту.
- `frontend/next.config.mjs` включат `output: "standalone"` только при
  `NEXT_OUTPUT=standalone` — обычный `npm run build` в `frontend/` не меняется.
- Next печёт rewrites в момент сборки, поэтому `API_INTERNAL_URL` в рантайме
  не читается — вместо этого Electron проксирует `/api/*` на backend (как
  Caddy в проде) и переписывает `Origin` на origin API: иначе любой
  POST/PUT/PATCH/DELETE получает 403 «Недопустимый источник запроса» (R66).

## Сборка

```bash
cd desktop
npm install
npm run prepare:backend   # заморозить backend (PyInstaller) → backend-dist/
npm run dist              # → dist/FuelRadar-Setup-<версия>.exe + latest.yml + .blockmap
npm run smoke             # быстрая проверка: окно + сервер + прокси + backend
npm run smoke:first-run   # то же + наполнение демо-каталога на первом запуске
```

`npm run dist` сам: рисует `build/icon.ico` из `frontend/public/icon.svg`,
замораживает backend, собирает standalone и упаковывает NSIS-установщик. Артефакты
(`dist/`, `server-dist/`, `backend-dist/`, `.backend-build/`, `build/`) не
коммитятся — см. `.gitignore`.

Smoke-прогон поднимает окно и проверяет те же адреса, что открывает окно, плюс
оголённый каталог через прокси: `FUELRADAR_SMOKE_BACKEND <состояние>`,
`FUELRADAR_SMOKE_STATIONS <сколько отдаёт /api/v1/stations>` (0 — рабочий backend
без данных, 7 — демо-фикстуры), а также путь панели «Данные» через тот же мост,
которым ходит интерфейс — `FUELRADAR_SMOKE_DB_BACKUP ok rows=<N>` (копия
локальной базы реально снимается) и `FUELRADAR_SMOKE_DB_MIGRATE unconfigured`
(перенос без внешней базы честно отказывает, а не изображает успех) — а также
сигнал о сборе через прокси, которым ходит главный экран:
`FUELRADAR_SMOKE_COLLECTION <состояние>` (`unplanned`/`stalled`/`overdue`/
`disabled` на пустом каталоге, `ok` после офлайн-наполнения — состояние не
выдумывается, проверяется его согласованность) — и `FUELRADAR_SMOKE_OK <адрес>`. Данные прогона
идут во временный каталог и удаляются — профиль оператора не трогается, а сбор по
расписанию прогон гасит сам (`COLLECT_IN_PROCESS=0`), чтобы он не ходил в сеть и
не зависел от доступности источников.

## Backend: автозапуск и честный экран (R97i)

Оболочка несёт только интерфейс — данные приходят с API. Чтобы окно не
показывало посреди интерфейса сырое «Backend недоступен (ECONNREFUSED)»,
при старте происходит вот что (`desktop/backend.cjs`, состояние видно в логе
как `[backend] <состояние> — …`):

1. **Проба** `GET <адрес>/health`. Отвечает — окно открывает интерфейс.
2. **Автозапуск.** Адрес локальный (`127.0.0.1`/`localhost`) и backend молчит →
   оболочка сама поднимает его тем же способом, что `make dev`
   (`<python> -m uvicorn app.main:app --host 127.0.0.1 --port <порт из адреса>`)
   и ждёт готовности до 60 с. Погашенный процесс — только свой: уже
   запущенный вручную (`make dev`) оболочка не трогает.
3. **Статус-экран.** Поднять не удалось (или адрес удалённый/автозапуск
   выключен) → вместо интерфейса — экран с адресом API и источником, каталогом
   и Python, списком проверенных мест, технической подробностью (код ошибки,
   хвост вывода процесса) и кнопками **«Повторить»** (перепроверить и, если
   нужно, запустить снова) и **«Открыть конфиг»** (создаёт шаблон
   `config.json` с найденными путями и открывает его). Перезагрузка страницы
   тоже перепроверяет backend — вручную запущенный сервер вылечивает окно.

### Встроенный backend: Python на машине не нужен

В собранном приложении backend едет ВНУТРИ установщика: `npm run prepare:backend`
замораживает `backend/` в самостоятельный бинарник (PyInstaller one-dir) и кладёт
его в `resources/backend/fuelradar-backend.exe` — ~60 МБ вместе с интерпретатором,
зависимостями и драйвером Postgres. Оболочка предпочитает именно его, поэтому на
машине пилота нет ни Python, ни venv, ни pip.

- Данные — в каталоге пользователя (`%APPDATA%\FuelRadar\data`), а не рядом с
  установкой: в Program Files писать нельзя. Там SQLite-база, история наблюдений
  (append-only, R17) и загрузки CSV из админки.
- `backend.seedRegion` — **регион пилота**, а не только ключ демо-данных: им же
  наполняется каталог из офлайн-фикстур на первом запуске (без сети — тогда
  первый кадр интерфейса уже с АЗС) и по нему же идёт сбор по расписанию
  (оболочка передаёт его встроенному backend как `--region`). Существующую базу
  наполнение никогда не трогает; без региона каталог остаётся пустым, сбор не
  запускается и об этом честно пишется в лог.
- Явные `backend.dir`/`backend.python` — пин для отладки: если они заданы,
  оболочка уважает их и встроенный бинарник не подставляет молча.
- **Сбор по расписанию идёт сам.** Отдельного процесса воркера в установленном
  приложении нет, поэтому расписание ведёт фоновый тикер самого backend
  (`app/worker/inprocess.py`, такт — `WORKER_TICK_SECONDS`, настройка
  `COLLECT_IN_PROCESS`, по умолчанию включена встроенным backend). Лок — тот же,
  что у `python -m app.worker`: если рядом всё-таки работает воркер, дублей не
  будет. Без этого каталог «остывал»: TTL статусов истекал, все АЗС становились
  UNKNOWN, а кнопка «Обновить источник» ставила задание, которое никто не
  исполнял. Выключить сбор можно `COLLECT_IN_PROCESS=0` или `backend.collect=false`
  (например, на машине заведомо без сети — тогда источники честно помечаются
  OFFLINE, а данные не трогаются).
- **Внешняя база — по желанию.** По умолчанию это локальная SQLite в каталоге
  данных. `backend.databaseUrl` (или `DATABASE_URL`) переключает встроенный
  backend на общий Postgres/PostGIS — драйвер psycopg едет в установщике, а
  `prepare-backend.mjs` проверяет его наличие отдельным запуском. Пароль не
  показывается ни в логе, ни на статус-экране, а демо-фикстуры первого запуска
  во внешнюю базу не пишутся вовсе.
- Сборка проверяет себя сама: `prepare-backend.mjs` запускает готовый бинарник на
  пустом каталоге данных (`--seed-offline`) и падает, если база не создалась, —
  установщик с нерабочим backend не соберётся.

Сам бинарник — это `backend/desktop_server.py`: `app.main:app` под uvicorn плюс
`--host/--port/--data-dir/--seed-offline/--backup-db/--migrate-db`. `.env` рядом
с ним намеренно не читается: в собранном приложении настройки приходят из
`config.json` оболочки. Запустить вручную (отладка, поддержка):

```bash
cd desktop
./backend-dist/fuelradar-backend/fuelradar-backend.exe --data-dir /tmp/fr --port 8000
./backend-dist/fuelradar-backend/fuelradar-backend.exe --seed-offline --region krasnodar --data-dir /tmp/fr
./backend-dist/fuelradar-backend/fuelradar-backend.exe --data-dir /tmp/fr --backup-db
./backend-dist/fuelradar-backend/fuelradar-backend.exe --data-dir /tmp/fr --migrate-db --to-database-url "postgresql+psycopg://user:пароль@host:5432/fuelradar"
```

### Данные: копия локальной базы и перенос в Postgres

Настройки → вкладка «Данные» (только в оболочке) — то, что нужно оператору до
того, как что-то сломалось:

- **Резервная копия** (`--backup-db`) — консистентный снимок локальной SQLite
  штатным онлайн-бэкапом: приложение продолжает работать, а копия не бывает
  «наполовину записанной». По умолчанию — `<данные>/backups/fuelradar-<UTC-штамп>.db`;
  в отчёте путь, размер, таблицы и число записей (а не просто «готово»).
  «Экспортировать копию…» — та же операция, но место выбирается системным
  диалогом сохранения (передать базу в поддержку, унести на другую машину).
- **Перенос во внешний Postgres** (`--migrate-db`) — когда `backend.databaseUrl`
  задан и база развёрнута, кнопка переносит накопленное (каталог, история
  наблюдений, настройки). Перенос идёт со СНИМКА локальной базы (согласованный
  момент времени), схему цели создаёт из тех же моделей, строки вставляет с
  пропуском конфликтов — поэтому повторный запуск безопасен и честно отвечает
  «вставлено 0, пропущено N». После данных накатываются идемпотентные миграции
  и сиды словарей, а SERIAL-последовательности цели догоняются до максимумов
  перенесённых id (иначе следующая же вставка приложения получила бы занятый id).
  Локальные данные не удаляются и приложение не переключается: когда перенос
  завершён, `backend.databaseUrl` уже настроен и backend работает с внешней базой.
  Без `backend.databaseUrl` кнопка не показывается — панель честно говорит
  «не настроено» и где это задать; пароль внешней базы наружу не отдаётся (R68).

Технически: оболочка запускает тот же бинарник в режиме «сделал и вышел»
(`backend.cjs::maintenanceCommand`), разбирает его ASCII-JSON-отчёт
(`parseMaintenanceReport`) и отдаёт в интерфейс по IPC
`fuelradar:db-status|db-backup|db-export|db-migrate|db-reveal`. В dev-запуске
оболочки те же команды выполняет `python desktop_server.py` из каталога backend
(если он есть и найден интерпретатор).

Сборка требует Python с зависимостями backend — на машине СБОРЩИКА, а не пилота
(заморозка интерпретатора и пакетов — задача сборочного окружения, а не поставки).
Переопределить интерпретатор: `FUELRADAR_BUILD_PYTHON`; переиспользовать готовый
артефакт: `FUELRADAR_BACKEND_SKIP_BUILD=1`.

### Куда оболочка ходит

Приоритет сверху; адрес и регион — данные, не код (R04/R81):

| Что | Переменная окружения | config.json | Иначе |
|---|---|---|---|
| Адрес API | `FUELRADAR_API_URL` | `apiBaseUrl` | `http://127.0.0.1:8000` |
| Автозапуск | `FUELRADAR_BACKEND_AUTOSTART` (`0` — выключить) | `backend.autostart` | включён |
| Встроенный backend | — (только сборка) | — | `resources/backend/fuelradar-backend.exe` |
| Каталог backend (с `app/main.py`) | `FUELRADAR_BACKEND_DIR` | `backend.dir` | `backend/` рядом с оболочкой (dev), `<userData>/backend` |
| Python с зависимостями | `FUELRADAR_PYTHON` | `backend.python` | `.venv` в каталоге backend/рядом, затем `python` из PATH |
| Каталог данных | `FUELRADAR_DATA_DIR` | `backend.dataDir` | `<userData>\data` |
| Регион пилота (наполнение и сбор) | `FUELRADAR_SEED_REGION` | `backend.seedRegion` | нет региона: каталог не наполняется, сбор не запускается |
| Внешняя база | `DATABASE_URL` | `backend.databaseUrl` | локальная SQLite в каталоге данных |
| Сбор по расписанию | `COLLECT_IN_PROCESS` (`0` — выключить) | `backend.collect` | включён (встроенный backend) |

```json
{
  "apiBaseUrl": "http://127.0.0.1:8000",
  "backend": {
    "autostart": true,
    "dataDir": "",
    "seedRegion": "krasnodar",
    "dir": "C:\\Projects\\Python\\fuelradar\\backend",
    "python": "C:\\Projects\\Python\\fuelradar\\backend\\.venv\\Scripts\\python.exe"
  }
}
```

`%APPDATA%\FuelRadar\config.json` (путь = `app.getPath("userData")`). Явно
заданный каталог/интерпретатор — это пин: указали в никуда — экран честно
скажет об этом, а не подменит другим каталогом молча.

Проверить без окна (удобно на машине пилота и в поддержке) — тот же код, что
у кнопки «Повторить», включая попытку автозапуска; код выхода 0 — отвечает,
3 — нет:

```bash
# Windows, собранное приложение
set FUELRADAR_BACKEND_STATUS=1 && "%LOCALAPPDATA%\Programs\FuelRadar\FuelRadar.exe"

# dev-запуск
cd desktop && FUELRADAR_BACKEND_STATUS=1 ./node_modules/electron/dist/electron.exe .
```

Строки вывода называют, чем именно поднят backend и куда он пишет данные:
`[backend] runtime: bundled|python`, путь к встроенному бинарнику и
`[backend] каталог данных: …`. Именно поэтому «окно говорит, что backend не
отвечает» разбирается по выводу, а не по догадкам.

Статус-экран для браузера недоступен (там нет моста оболочки): он отдаётся
прокси по пути `/__fuelradar/backend` только пока backend не отвечает, а `/api/*`
в это время отвечает JSON-ошибкой `Backend недоступен (<причина>)`.

## Вход через Telegram (R66/R97i)

- Backend: `TELEGRAM_BOT_TOKEN` в `.env` — без него `POST /auth/telegram`
  честно отвечает «не настроено» (R97i), приложение не падает.
- Frontend: `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` в `frontend/.env.local` —
  публичное имя бота для виджета; имя не секрет, токен на фронт не попадает.
- Оболочка: виджет грузится с `telegram.org`, открывает popup
  `oauth.telegram.org` — такие попапы разрешены дочерними окнами
  (`desktop/main.cjs`), остальные внешние ссылки уходят в системный браузер,
  `tg://` — в Telegram-клиент. Cookie-сессия живёт в профиле пользователя.

## Автообновление

- `electron-updater`, NSIS, `autoDownload` + установка при выходе; проверка
  при старте и раз в 4 часа; уведомление «обновление загружено».
- Фид — **Releases приватного репозитория** `Sovero/fuelradar`
  (`build.publish` = `provider: github`); owner/repo запекаются при сборке в
  `resources/app-update.yml`. Публикация релиза:
  ```
  gh release create vX.Y.Z dist/FuelRadar-Setup-X.Y.Z.exe \
    dist/FuelRadar-Setup-X.Y.Z.exe.blockmap dist/latest.yml
  ```
- **Токен фида** (репозиторий приватный): fine-grained PAT с единственным
  правом **Contents: Read-only** только для этого репозитория
  (<https://github.com/settings/personal-access-tokens/new>). Токен берётся из
  надёжного места, а не из файла, который человек руками положил в рабочую
  копию: afterPack (`scripts/feed-token.cjs` → `patch-feed-token.cjs`) упакует
  найденное в `resources/update-feed-token` и рядом положит только отпечаток
  (`resources/update-feed-token.source`, SHA-256[:12]) — сверить, что в сборке
  именно ожидаемый секрет, можно, вытащить его из отпечатка — нет.
- В рантайме `main.cjs` читает токен и переключает фид на
  `setFeedURL({provider:"github", private:true, token})` →
  PrivateGitHubProvider работает через **api.github.com** (`releases/latest`
  + asset API). Обычные github.com-эндпоинты (atom-фид, `/releases/latest`,
  download-ссылки) API-токены не принимают — для приватного репозитория они
  всегда 404, поэтому `addAuthHeader` с публичной схемой здесь не работает.
- **Токена нет** → сборка работает, автообновление в ней честно отключено
  (при старте пишется `[updates] токен фида не упакован`, IPC возвращает
  `supported: false` — R97i). Токен истёк/отозван → апдейтер молча пишет
  ошибку в лог, приложение работает как обычно.

### Откуда сборка берёт токен фида

Порядок источников (первый найденный побеждает; если ничего не нашлось — сборка
соберётся без автообновления и честно об этом скажет):

| # | Источник | Как задать |
|---|---|---|
| 1 | Переменная окружения | `UPDATE_FEED_TOKEN` — путь CI (секрет репозитория) и любой внешний секрет-менеджер |
| 2 | Файл вне репозитория | `UPDATE_FEED_TOKEN_FILE=%USERPROFILE%\\.fuelradar\\update-feed-token` |
| 3 | Хранилище учётных данных Windows | `cd desktop && npm run feed:token:store` (токен читается из stdin, цель `FuelRadar/update-feed-token`) |
| 4 | `desktop/.update-feed-token` | прежний путь: ещё работает, но помечен устаревшим — это секрет внутри рабочей копии |
| 5 | Токены инструментов (`gh auth token`, сохранённый git-креденшел) | только с `FUELRADAR_ALLOW_SHARED_FEED_TOKEN=1`: у них широкие права (`repo`), приложению нужно лишь чтение |

Проверить, что найдётся перед сборкой, и не запускать сборку вообще:

```bash
cd desktop
npm run feed:token:status              # что опрошено, источник и отпечаток
npm run feed:token:status -- --require # код 1, если токена нет (так делает CI)
npm run feed:token:store               # сохранить свой read-only PAT в хранилище Windows
npm run feed:token:forget              # удалить запись (ротация/отзыв)
npm run feed:token:selfcheck           # проверить само хранилище, не трогая рабочий токен
npm test                                # контракт цепочки источников (node --test)
```

Любая проверка хранилища выполняется на **отдельной** цели (`FuelRadar/update-feed-token--selfcheck`): она пишет и удаляет секрет, поэтому на рабочей цели стёрла бы настоящий токен фида. Команды принимают `--target <имя записи>`, а имя рабочей цели переопределяется переменной `FUELRADAR_WINCRED_TARGET` — так самопроверка и тесты не пересекаются с рабочим токеном.

Секрет нигде не передаётся аргументом команды и не логируется: в отчётах только
источник и отпечаток. Если файл из `UPDATE_FEED_TOKEN_FILE` всё-таки лежит
внутри рабочей копии репозитория, сборка предупредит — смысл настройки в том,
чтобы секрет не лежал рядом с кодом.
- В dev-режиме обновления не проверяются (проверять не с чего — честно).
- Проверка обновления end-to-end: установить сборку версии N (с токеном),
  опубликовать релиз N+1 по инструкции выше, запустить приложение N →
  «обновление загружено», закрыть → при следующем запуске версия N+1.
- Релизный workflow GitHub Actions теперь подписывает Windows-артефакты
  Authenticode-сертификатом из секретов `WINDOWS_CERTIFICATE_BASE64` и
  `WINDOWS_CERTIFICATE_PASSWORD`, а перед публикацией проверяет статус подписи.
  Для доверия SmartScreen сертификат должен быть выдан доверенным центром
  сертификации; сам факт подписи не гарантирует мгновенное исчезновение
  предупреждения для нового издателя — репутация подписи накапливается.

### Самопроверка фида (R97i)

`electron-updater` на вопрос «почему нет обновлений» отвечает одинаково в трёх разных
случаях, поэтому оболочка проверяет фид сама (`desktop/feed-status.cjs`) и пишет
результат в лог при старте:

```
[updates] фид: ok — Фид доступен: последний релиз v0.1.1, обновляться не с чего.
```

Состояния: `ok` (фид доступен, релиз найден), `no-token` (токен не упакован),
`no-config` (нет owner/repo), `no-access` (токен не принят или нет прав
Contents: Read-only), `no-release` (доступ есть, релизов нет), `rate-limited`
(GitHub ограничил лимит API), `network` (нет сети), `http-error` (иной код),
`dev-run` (dev-запуск, проверять нечего). Различать 404 «нет релизов» и 404 «нет
доступа» приходится вторым запросом (доступ к списку релизов есть только с правами) —
поэтому второе состояние и подписано явно.

То же состояние видно во вкладке «Обновления» настроек: текст причины, отпечаток
упакованного токена (сверить можно, секрет не раскрывается), время проверки и
подсказка с технической подробностью (`HTTP 401`, `список релизов → 404`). Если
сборка оболочки старше этой проверки, панель честно пишет «не сообщает состояние
фида», а не показывает успех.

Проверить фид **без запуска окна** (удобно на машине пилота и в поддержке):

```bash
# в собранном приложении (Windows):
set FUELRADAR_FEED_STATUS=1 && "%LOCALAPPDATA%\Programs\FuelRadar\FuelRadar.exe"

# в dev-запуске:
cd desktop && UPDATE_FEED_TOKEN=<пат> FUELRADAR_FEED_STATUS=1 npx electron .
```

Приложение выводит строку `FUELRADAR_FEED_STATUS <состояние> <причина>` и отпечаток
токена, затем выходит: код 0 — фид доступен, 3 — нет. Окно при этом не открывается.

В dev-режиме (`npx electron .`) самопроверка тоже работает: токен берётся из
`UPDATE_FEED_TOKEN` (только вне пакета), а конфиг — из последней локальной сборки
(`dist/win-unpacked/resources/app-update.yml`).

### Подпись Windows-релизов

В настройках репозитория добавьте два Actions secrets:

- `WINDOWS_CERTIFICATE_BASE64` — содержимое PFX/P12, закодированное в base64;
- `WINDOWS_CERTIFICATE_PASSWORD` — пароль PFX.

PFX не хранится в Git и не включается в логи. Workflow восстанавливает его
только в `${RUNNER_TEMP}`, передаёт путь electron-builder через стандартные
`WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD`, затем удаляет сертификат после сборки.
Перед публикацией `Get-AuthenticodeSignature` требует статус `Valid` у
установщика. Используйте OV/EV code-signing certificate с timestamp-подписью;
самоподписанный сертификат пригоден только для внутренних тестов и не уберёт
предупреждения SmartScreen у пользователей.

### Релиз через GitHub Actions

Для автоматической сборки без локальной Windows-машины workflow
`.github/workflows/desktop-release.yml` запускается на каждый тег вида `vX.Y.Z`:

1. версия тега должна совпадать с `desktop/package.json`;
2. workflow ставит зависимости через `npm ci` и собирает NSIS-установщик;
3. публикует `FuelRadar-Setup-<версия>.exe`, `.blockmap` и `latest.yml` в GitHub Release.

Так как репозиторий приватный, в настройках репозитория нужен secret
`UPDATE_FEED_TOKEN`: fine-grained PAT только для `Sovero/fuelradar` с правом
**Contents: Read-only**. Workflow передаёт его в окружение сборки (файл с токеном
в рабочей копии больше не создаётся) и до сборки проверяет наличие тем же кодом,
что читает токен,
`npm run feed:token:status -- --require` — сборка без секрета не уедет в релиз с
молча отключённым автообновлением. Токен попадает в упакованный установщик (иначе
автообновление из приватного релиза невозможно) и в логи не выводится; на раннере
чистится сертификат подписи.

Пример публикации новой версии:

```bash
# сначала изменить desktop/package.json и закоммитить версию
# затем создать и отправить тег
git tag v0.1.2
git push origin v0.1.2
```

Если Release с таким тегом уже существует, workflow заменит его desktop-артефактами.
Для production рекомендуется не переиспользовать опубликованные теги, а создавать
новый patch/minor tag.
