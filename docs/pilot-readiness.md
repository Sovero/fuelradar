# Готовность к production-запуску пилота (Краснодар)

Чек-лист для перевода FuelRadar из режима разработки в эксплуатацию пилота.
Пункты привязаны к реальным файлам и переменным репозитория — не к абстрактным
«настроить мониторинг». Порядок разделов совпадает с рекомендуемым порядком
выполнения: секреты → деплой → источники → люди → наблюдение → бэкапы → гейт.

Коротко о разнице с dev-жизнью проекта, из-за которой чаще всего «открыли, а не
работает»:

- **Входа больше нет вообще.** Пользователей в приложении не осталось: всё —
  карта, админка, настройки — открыто тому, кто его запустил. Секретами остаются
  только ключи каналов (`TELEGRAM_BOT_TOKEN`, VAPID) в `.env`; Telegram-дайджест
  настроекся через UI (Настройки → Telegram) и присылает сводку по расписанию.
- **CORS в проде не нужен.** За общим Caddy браузер видит один origin, поэтому
  `CORS_ORIGINS` не задаётся; всплывает это только при раздельном запуске
  (`uvicorn` + `next dev`) — тогда POST/PUT/PATCH/DELETE отдают «Недопустимый
  источник запроса».
- **Воркер перестаёт быть «ещё одним процессом».** Сбор идёт только через
  `worker` (R83), и без его контроля за данными никто не следит: они молча
  протухают в `UNKNOWN` по TTL.
- **Env в docker должно быть продублировано явно.** Compose передаёт в контейнер
  только перечисленные переменные: значение из корневого `.env` не появляется в
  контейнере само по себе (см. п.1.3 — там же реальный пробел).

## 1. Секреты и конфигурация

### 1.1. Обязательный минимум (compose упадёт на старте без них)

- [ ] `POSTGRES_PASSWORD` — пароль БД;
- [ ] `APP_DOMAIN` — HTTPS-домен (его Caddy использует для сертификата и
      `PUBLIC_APP_URL`).

`docker-compose.prod.yml` использует `:?set in .env`, то есть падение на старте —
это и есть проверка, что они заданы.

### 1.2. Остальное

- [ ] `DEBUG=false` — честный прод-режим;
- [ ] HTTPS на домене;
- [ ] `DATABASE_URL` — prod-профиль подставляет PostGIS сам;
- [ ] `REDIS_URL=redis://redis:6379/0` — prod-профиль подставляет сам; без него
      `/metrics` у api не увидит счётчики воркера (тихий откат на in-memory);
- [ ] `RATE_LIMIT_PER_MINUTE=120`, `ADMIN_RATE_LIMIT_PER_MINUTE=30` — не выключать;
- [ ] регион как данные (R04/R81): `DEFAULT_REGION_CITY=Краснодар`,
      `DEFAULT_REGION_RADIUS_KM=10`; во frontend — `NEXT_PUBLIC_DEFAULT_MAP_LAT`,
      `NEXT_PUBLIC_DEFAULT_MAP_LON` в `frontend/.env.local`;
- [ ] каналы по желанию: `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (Web Push; после
      настройки `/api/v1/meta` отдаёт `push.enabled=true`);
- [ ] `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` — в `frontend/.env.local` (сам токен на
      фронт не попадает никогда).

Отсутствующий секрет канала — не ошибка запуска: приложение отвечает «не
настроено» (R97i) и работает дальше.

### 1.3. Файловые источники в контейнерах (исправлено в compose)

`api` и `worker` — разные контейнеры с разными файловыми системами, поэтому
админский импорт CSV работает только при общем каталоге. В базовом
`docker-compose.yml` настройка одна и наследуется прод-профилем:

```yaml
# docker-compose.yml (якорь x-import-files — общая переменная api и worker)
  api:
    environment:
      FUELRADAR_CSV_UPLOAD_DIR: ${FUELRADAR_CSV_UPLOAD_DIR:-/data/import}
  worker:
    environment:
      FUELRADAR_CSV_UPLOAD_DIR: ${FUELRADAR_CSV_UPLOAD_DIR:-/data/import}
      NETWORK_LISTS_URLS: ${NETWORK_LISTS_URLS:-}   # пусто → источник «не настроено»
  # оба сервиса монтируют fuelradar-data:/data
```

Правило: админка (процесс `api`) пишет загрузку в каталог
`FUELRADAR_CSV_UPLOAD_DIR`, а источник `network_import` в процессе воркера
читает оттуда `<каталог>/catalog-enrichment.csv` — **второй переменной пути к
файлу нет**, имя фиксировано эндпоинтом `/admin/catalog-gaps/import-csv`. Правок
`.env` для этого не требуется. Защита от рассинхронизации:
`backend/tests/test_compose_config.py` (общая переменная обоих сервисов, общий том
для обоих профилей, отсутствие второй настройки пути в compose).

- [ ] Без docker сквозной прогон (два процесса, две ФС):
      `cd backend && python scripts/e2e_csv_import_split.py` — фаза, где воркер
      смотрит в другой каталог, обязана упасть `FileNotFoundError`, фаза с общим
      каталогом — дать `DONE` и обогащённые станции;
- [ ] С docker (если он есть на хосте): `docker compose -f docker-compose.yml
      -f docker-compose.prod.yml config` — `FUELRADAR_CSV_UPLOAD_DIR` одинаковый
      у `api` и `worker`; затем живой цикл:
      «Покрытие каталога» → «Импортировать CSV» → «Журнал загрузок» → «Слияния»;
- [ ] Если планируются HTTP-списки сетей — задать `NETWORK_LISTS_URLS` в `.env`
      и активировать источник `network_lists` в админке;
- [ ] `OVERPASS_ENDPOINT` правки не требует — у него рабочий публичный дефолт.

## 2. Деплой и периметр

- [ ] `make compose-prod` поднимается с первого раза: `api`, `worker`,
      `db` (PostGIS), `redis`, `frontend`, `proxy` (Caddy);
- [ ] CI зелёный на коммите релиза (`.github/workflows/ci.yml`: ruff, pytest,
      typecheck, build);
- [ ] HTTPS: A-запись домена, открытые 80/443, сертификат выдан (Caddy сам);
- [ ] `GET /health` → `{"status":"ok"}`; `GET /ready` → `{"status":"ready","db":"ok"}`;
- [ ] `GET /metrics` непустой **у api**: есть `source.<code>.requests/errors/records`
      (если пусто — не подхватился `REDIS_URL`);
- [ ] SSE через Caddy: открыть карту в двух вкладках, изменить данные (отчёт или
      сбор) — обновление должно прийти без перезагрузки (стрим не буферизуется);
- [ ] smoke-сценарий брифа: вход → фильтр «АИ-95» → карта → карточка станции
      (статус + confidence + score) → «Сообщить» → статус пересчитался.

## 3. Источники данных и качество каталога

- [ ] Каталог наполнен: `docker compose exec api python -m cli.seed --region krasnodar`
      (в dev-проверках — `--offline` на фикстурах);
- [ ] Админка → «Источники»: `osm_overpass`, `network_import`, `user_reports` —
      ACTIVE с health ONLINE; `network_lists` — NOT_USED, пока не заданы URL;
- [ ] **Цикл обогащения каталога проверен целиком**: «Покрытие каталога» →
      «Скачать CSV для заполнения» → заполнить → «Импортировать CSV» → «Журнал
      загрузок» → «Слияния» (подтвердить REVIEW-кандидатов);
- [ ] Интервал файлового источника адекватен. В сиде у `network_import` потолок
      5 мин (файл без сети), но **сид идемпотентен и существующую строку не
      перезаписывает**: в развёрнутой ранее БД проверьте интервал в
      «Источники» → «Изменить» — при суточном потолке повторный ручной импорт
      ждёт до следующих суток. Плашка импорта показывает фактическое время
      запуска задания (`next_run_at`), backoff источника при импорте сбрасывается
      (аудит `csv_import` → `backoff_reset`);
- [ ] Trust источников соответствует доверию к данным (R18/R95i): для OSM ниже,
      для официальных списков сети — выше;
- [ ] Мера покрытия зафиксирована по факту (админка → «Покрытие» /
      «Покрытие каталога»): сколько АЗС с брендом/адресом/телефоном.

## 4. Доступ и Telegram-подписка

- [ ] Интерфейс открыт без входа: карта, админка и настройки отвечают сразу;
- [ ] Telegram-дайджест настроен: токен бота в UI или `.env`, чат определён
      (боту написали сообщение), интервал больше 0; тестовая сводка доставлена;
- [ ] Проверено, что сводка не дублируется при запущенных api и worker
      (отправляет только владелец общего лока);

## 5. Мониторинг и эксплуатация

- [ ] Внешний мониторинг на `/ready` (не `/health`): он проверяет БД;
- [ ] **Liveness воркера**: смещение `source_health.last_success_at` не растёт →
      сбор встал. Алерт на «нет успешных сборов N часов» (без него данные тихо
      протухают в `UNKNOWN`, а карта выглядит «рабочей»);
- [ ] Деградация источников видна: админка → «Источники» (health
      OFFLINE/RATE_LIMITED/AUTH_ERROR + число сбоев), «Журнал загрузок» (ошибки);
- [ ] Показатели шума данных (админка → «Покрытие»): станции без данных
      (`no_data`) и доля `coverage_percent`, а в Fuel Availability Index —
      `excluded_unknown`; рост этих чисел = проблема данных, а не косметика;
- [ ] `/metrics` снимается внешним сборщиком (Prometheus-совместимый формат не
      заявлен — снимок JSON; для пилота достаточно периодического опроса);
- [ ] Аудит: «Журнал действий» пишется (`csv_import`, `dedup_merge`, `role_change`,
      `source_update`, `block_user`); попытки входа с неверными данными
      фиксируются на уровне rate-limit и логов;
- [ ] Регламент на время пилота: кто смотрит health/журналы и что делает при
      деградации (деактивировать источник статусом NOT_USED — данные не удаляются, R84).

## 6. Бэкапы и восстановление

- [ ] Ежедневный дамп: `docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T db pg_dump -U fuelradar -d fuelradar -Fc > backups/fuelradar-$(date +%F).dump`;
- [ ] Ротация ≥ 7 дней и копия **вне** хоста;
- [ ] Бэкапятся volume `postgis-data` (БД) и `caddy-data` (сертификаты);
- [ ] **Тест восстановления** на чистом контейнере из свежего дампа — бэкап без
      restore-теста бэкапом не считается;
- [ ] После восстановления проверена история: `fuel_observations` на месте
      (наблюдения append-only, R17 — потеря истории недопустима).

## 7. Desktop-приложение (если раздаём пилотным операторам)

- [ ] `make desktop-dist` собирает NSIS-установщик
      (`desktop/dist/FuelRadar-Setup-<v>.exe`);
- [ ] автообновление: токен фида берётся из надёжного места — переменная
      `UPDATE_FEED_TOKEN`, файл вне репозитория (`UPDATE_FEED_TOKEN_FILE`) или
      хранилище учётных данных Windows (`npm run feed:token:store`), а не из
      файла в рабочей копии; фид — Releases приватного репозитория.
      Проверка до сборки: `cd desktop && npm run feed:token:status`
      (в CI тот же вызов с `--require`: без секрета релиз не собирается),
      внутри сборки — отпечаток в `resources/update-feed-token.source`;
- [ ] релиз по тегу идёт из GitHub Actions (`.github/workflows/desktop-release.yml`),
      а не только с локальной машины;
- [ ] на установленном приложении проверена вкладка «Обновления» (версия + ручная
      проверка + состояние фида) и вход в систему;
- [ ] самопроверка фида на машине пилота без запуска окна:
      `set FUELRADAR_FEED_STATUS=1 && FuelRadar.exe` → код 0 и `FUELRADAR_FEED_STATUS ok`;
      при `no-access` сборка пересобирается с рабочим read-only токеном, при
      `no-release` сначала публикуется релиз (в логе и вкладке причина названа явно);

## 8. Гейт готовности (не запускать пилот, пока не выполнено)

| # | Критерий | Проверка |
|---|----------|----------|
| G1 | Деплой воспроизводим | `make compose-prod` с нуля, `/ready` = ok |
| G2 | HTTPS и cookie | домен открывается по HTTPS, `COOKIE_SECURE=true`, `DEBUG=false` |
| G3 | Каталог покрыт | наполнен по Краснодару, покрытие по бренду/адресу зафиксировано до/после обогащения |
| G4 | Данные живые | сбор идёт по расписанию, `source_health.last_success_at` свежий, станций без данных (`no_data` в «Покрытии») меньше 15% |
| G5 | Доступ и подписка | интерфейс открыт без входа; Telegram-дайджест доставляет сводку по расписанию |
| G6 | Безопасность | секреты только в `.env`; rate limits включены; журнал админ-действий ведётся |
| G7 | Бэкап | успешный restore-тест за последние 72 часа |
| G8 | Наблюдаемость | внешний мониторинг `/ready` + алерт на остановку сбора |

Пороговые значения G4 — цель, которую стоит согласовать перед запуском: они
зависят от плотности источников в регионе и от того, сколько операторов
заполняют данные руками. Единственное, что не обсуждается: `UNKNOWN` и
`UNAVAILABLE` не смешиваются ни при каком пороге (R15).

## 9. Открытые вопросы перед запуском

- **Конфигурация источников в compose** (п.1.3) — до фикса админский импорт CSV
  в Docker не работает.
- **Доступ к интерфейсу открыт всем, кто имеет сетевой доступ к сервису** —
  закрывать периметр (VPN/firewall/ограничение по IP на Caddy), если пилот
  смотрят не только доверенные люди.
- **Rate limit источника** — жёсткий потолок (R54): он осознанно действует и для
  ручных заданий; если операторам нужно чаще, интервал меняется в «Источники»,
  а не обходится кодом.
- **Прогноз и heatmap — эвристики, не ML.** Они считают по снэпшоту
  аналитики (`is_forecast=true`); при малой истории честно отвечают «мало
  данных» — это ожидаемое поведение пилота, а не дефект.
