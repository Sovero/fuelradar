# Ручное обогащение каталога (CSV-импорт)

`krasnodar-unnamed-template.csv` — заготовка для оператора: 11 АЗС Краснодара,
которые в OSM не имеют ни названия, ни бренда, ни оператора. Заполняется вручную
и подаётся в активный файловый источник `network_import` — через админку
(«Импортировать CSV», основной путь) или файлом на диске (переопределение
`NETWORK_IMPORT_PATH`).

## Как заполнить

1. Для каждой строки откройте `osm_url` (карта OSM с этой точкой) и определите
   фактическую сеть/название/адрес (визуально, по панораме или справочникам).
2. Заполните колонки `brand` (Лукойл, Роснефть, Газпромнефть, РусОйл…),
   `name`, `address`, `phone`. Пустые значения оставлять можно — такие поля
   просто останутся без данных.
3. **Колонку `ref` не менять** — это id объекта OSM, по нему дедуп свяжет
   импортированную запись с OSM-записью той же станции (координаты совпадают
   до сантиметров).
4. Изменение `brand` меняет внешний id записи (`<бренд>-<ref>` вместо
   `station-<ref>`): дедуп корректно сольёт старую и новую записи по
   координатам, потерь нет.

## Как дедуп свяжет CSV с OSM

- OSM-станция **именованная** (есть название/бренд) → совпадение координат и
  бренда автоматически проходит порог слияния: запись сольётся с OSM-станцией
  без участия человека;
- OSM-станция **безымянная** (как раз строки этой заготовки) → совпадение
  координат с пустой OSM-стороной даёт ~0.75 балла — ниже порога авто-слияния
  (0.85): тихо сливать недостаточно доказано, и запись попадает в **очередь
  дедупа** (REVIEW). Это защита от ошибочных слияний (R10): подтвердите пару
  вручную — админка → «Очередь дедупа» → подтвердить слияние CSV-записи с
  OSM-записью (правильная пара видна по координатам и `osm_url`).

Сквозная проверка обеих ветвей — `backend/scripts/e2e_manual_enrich.py`
(офлайн, запускается: `cd backend && python scripts/e2e_manual_enrich.py`).

## Как подать файл

### Через админку — основной путь, без правки .env

1. Админка → «Покрытие каталога» → **«Скачать CSV для заполнения»**: система
   собирает заготовку сама — по станциям с пробелами, `brand`/`address`
   предзаполнены из источника, `ref`/`osm_url` на месте;
2. заполнить недостающие колонки (см. «Как заполнить»);
3. **«Импортировать CSV»** на той же вкладке: файл валидируется продакшен-
   парсером ещё до записи на диск (битый файл → 422, ничего не сохранено),
   затем сохраняется как `catalog-enrichment.csv` в каталог загрузки и ставит
   задание сбора P1 (trigger=manual) — синхронного сбора нет (R83);
4. результат — «Журнал загрузок», подтверждение слияний — вкладка «Слияния»
   (см. «Как дедуп свяжет CSV с OSM»), действие журналируется в «Журнале
   действий» (`csv_import`: кто, когда, сколько строк).

Настройка одна: каталог загрузки `FUELRADAR_CSV_UPLOAD_DIR`. Админка пишет в него
файл `catalog-enrichment.csv`, а источник `network_import` читает **оттуда же** —
отдельной переменной с путём к файлу нет. **В docker compose это настроено из
коробки** (`docker-compose.yml`: одна переменная `FUELRADAR_CSV_UPLOAD_DIR=/data/import`
у `api` и `worker`, оба сервиса монтируют том `fuelradar-data` в `/data`) —
править `.env` не нужно, ни разу. Проверяет инвариант
`backend/tests/test_compose_config.py`, а сквозной прогон имитации
контейнерного разделения (два процесса, две ФС, без docker) —
`cd backend && python scripts/e2e_csv_import_split.py`.

Своё значение — только если каталог вынесен в другое место (тогда оно должно быть
одинаковым у api и worker):

```bash
# без docker (путь от рабочего каталога backend):
FUELRADAR_CSV_UPLOAD_DIR=data/import

# docker, свой каталог (например, хост-папка внутри контейнеров):
FUELRADAR_CSV_UPLOAD_DIR=/data/import
```

После первичной настройки каждый импорт из админки перезаписывает этот же
файл — `.env` больше не правится. В git загрузки не попадают: каталог исключён
(`.gitignore`), в репозитории живёт только шаблон `krasnodar-unnamed-template.csv`.

**Как проверить, куда именно пишет и откуда читает система** (без лазания в `.env`):

- вкладка **«Источники»** — под названием `network_import` строка «Читает файл:»:
  полный путь, время последней правки и пометка, если путь задан явно
  (тогда это `NETWORK_IMPORT_PATH`, и импорт из админки пойдёт в другой файл);
- вкладка **«Покрытие каталога»** — блок «Файл источника»: тот же путь плюс две даты,
  которые нельзя путать: «Обновлён» — когда файл правили (импорт из админки),
  «Последний успешный сбор» — когда источник последний раз прочитал его. Если файл
  новее сбора, система прямо говорит, что данные на диске, но воркер их ещё не
  забрал (задание — в «Журнале загрузок»).

### Без админки — файл с диска (`NETWORK_IMPORT_PATH`)

Путь вне каталога загрузки (готовый CSV/JSON, а не загрузка из админки):

```bash
# .env (backend):
NETWORK_IMPORT_PATH=data/import/krasnodar-unnamed-template.csv
```

Если переменная не задана, источник читает загрузку админки из каталога выше.
В docker compose она не прокидывается в контейнеры (там настройка одна — каталог
загрузки): файл вне каталога кладите в `FUELRADAR_CSV_UPLOAD_DIR` под именем
`catalog-enrichment.csv`, либо допишите переменную в свой compose-оверлей.

Перезапустить api+worker. Источник `network_import` уже ACTIVE — воркер
подхватит файл по расписанию (обычный интервал сбора — раз в час, R53) либо
сразу: админка → «Источники» → `network_import` → «Обновить сейчас».

Импортированные записи в обоих вариантах проходят дедуп и появляются в
мастер-каталоге с заполненными брендами/адресами.

**Что с отсрочкой задания** (проверено живым прогоном). Две причины отсрочки
ведут себя по-разному:

- **backoff** (расписание повторных попыток после сбоев) — импорт из админки его
  **сбрасывает**: явный запрос оператора не ждёт, пока источник «отдохнёт». Сам
  факт сброса не теряется — «Журнал действий» → `csv_import` → `backoff_reset`.
- **потолок частоты источника** (`min_interval_minutes`, R54) — остаётся в силе:
  воркер не станет обращаться к источнику чаще его rate limit. Если интервал ещё
  не истёк, задание честно подождёт, и плашка импорта сразу скажет об этом время
  («воркер возьмёт задание не раньше …»), статус — в «Журнале загрузок».
  У файлового `network_import` интервал в сиде низкий (5 мин, как у
  `user_reports` — сеть не используется), менять его: «Источники» → «Изменить».
  Плановый сбор при этом не учащается — его такт задаёт `collect_default_minutes`.

## Формат

CSV, заголовки — алиасы парсера (`app/sources/network_import.py`):
`name, brand, lat, lon, address, phone, ref, city, region` (русские/английские
варианты принимаются). Кодировка UTF-8. Координаты — десятичные градусы WGS84,
точка — «.».

Служебная колонка `osm_url` допустима и парсером игнорируется — и заготовка,
и экспорт «Скачать CSV для заполнения» из админки кладут её в файл (формат
экспорта совпадает с форматом заготовки).
