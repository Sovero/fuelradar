# Спецификация: FuelRadar

Задача и решение — ниже. Полный список требований — в `manifest.md`; каждый пункт манифеста
прослеживается до раздела спецификации в таблице «Покрытие манифеста» в конце документа.
Источники данных — отдельный артефакт `research-sources.md` (R89 — первым артефактом).

Разделы §1–§21 соответствуют ссылкам «spec §N» в манифесте. В каждой истории: метка
(происхождение), история вида «Как <кто>, я <что>, чтобы <зачем>» и строка приёмки.
Метки `R##.n` — углубление требования брифа (неограниченно). Метки `A## → R##` — добавленные
возможности с родителем.

Глубина: **deep** — для каждого требования проходит восемь измерений (первый запуск,
пусто, неверный ввод, сбой, прерывание, рост, границы, последствия); где измерение не
применимо, стоит «—». Итог прохода — матрицы в конце каждого раздела.

---

## Задача

Водитель в регионе дефицита топлива (пилот — Краснодар) открывает приложение и спрашивает:
«Где поблизости **сейчас** действительно есть нужный мне бензин?» Он хочет знать: есть ли
топливо, **насколько этой информации можно верить**, есть ли очередь и сколько времени уйдёт,
чтобы доехать и заправиться. Сегодня ответы разбросаны по картам, чатам и слухам; карты
показывают «есть АЗС», но не «есть бензин», а устаревшее или выдуманное «топлива нет» хуже,
чем честное «нет данных».

## Решение

FuelRadar — PWA, которая ведёт **собственный мастер-каталог АЗС** (объединение нескольких
независимых источников с дедупликацией — ни один внешний сервис не является источником
истины), отделяет **факт существования станции** (Discovery) от **факта наличия топлива**
(Availability), честно различает «нет» и «не знаю», оценивает достоверность каждого статуса
(Confidence 0–100% с объяснением «почему»), показывает очереди и ETA, ранжирует станции
по FuelRadar Score и уведомляет пользователя о значимых изменениях по его правилам.

MVP-формула: **«Где сейчас поблизости с достаточной достоверностью есть нужный мне бензин?»**
(R91). Всё, что не служит этому вопросу, в MVP не входит и отложено (см. §21).

Принципы, из которых не выводится ни одного исключения в коде:
- наличие топлива определяется **только наблюдениями и правилами**; LLM/модель не решает
  «бензин есть» на основе отсутствующих данных (R42);
- «нет данных» никогда не превращается в «топлива нет» и наоборот (R15, §4);
- недоступность одного источника не роняет систему и не портит данные (R84, §6);
- система работает в любом городе/регионе без изменения кода — регион это конфигурация,
  не константа (R81, §18).

| 7 | R59.1 | …и я могу заменить картографический провайдер, не трогая логику | слой карты абстрагирован (§16 R61); бизнес-логика не знает провайдера |
| 8 | R82.1 | …и один тяжёлый запрос не уронил всех | rate limiting и кэширование §12, §15 |
| 9 | A01 → R94i | Как администратор, я запускаю одну команду `seed`, чтобы наполнить каталог по bbox и проверить систему без ожидания планировщика | CLI наполняет каталог из OSM + импортов по заданному региону, выводит счётчики и ошибки |

**Решения по реализации**
- Модульный монолит: модули `stations`, `sources`, `normalization`, `dedup`, `fuel_status`,
  `confidence`, `geo`, `monitoring`, `alerts`, `reports`, `analytics`, `admin`. Один процесс
  API + воркер; границы модулей — через внутренние сервисы, не через микросервисные вызовы.
  Почему: проще разворачивать/тестировать, бриф §82 прямо рекомендует.
- Конвейер каталога: `source_records → candidates (нормализация) → дедупликация → master stations`.
  Каждая ступень идемпотентна и перезапускаема. Почему: R08.2 — частичный успех не теряется.
- Агрегированное состояние для карты: таблица `station_current_status` (§3), карта не считает
  по истории. Почему: R82 — целевые 500 мс без сканирования миллионов наблюдений.
- PWA (Next.js) читает только публичный API `/api/v1`; весь сбор — на backend. Почему: R83, R68.

- Минимальная модель станции: `station_id`, `brand_id`, `canonical_name`, `lat/lon` (PostGIS

- Все координаты — PostGIS `geography` + spatial index (R82).
